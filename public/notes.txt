Why do we need to specify a key in react ?

KEY ANALOGY : 
File names in a folder and JSX keys in an array serve a similar purpose.

A key acts as a unique identifier of the item among its siblings. Even if the position of this item gets reordered due to sorting/insertion/deletion - the key lets React identify the item throughout its lifetime. 

2 rules of keys to be followed : 

  1. keys should always be unique - tbhi toh item ko properly identify krpayegi among its siblings 

  2. keys should not change - if keys changes everytime, then it wont match on rerenders and poora dom tree dobara recreate hoga and koi user input hui toh woh loose hojayegi + it will be very slow ( whole purpose of react will fail here !! )

Pitfalls : 

  1. Do not use array index as keys - coz jab elements reorder/insert/delete hote toh items upar neeche hote and indexing change hojati - violates our rule 2 that keys should not change - causes bugs 

  2. Do not generate keys on the fly e.g. with key={Math.random()} - again keys will change and never match up between renders, dom recreated everytime - slow krdega applicaiton ko + violates rule 2. 

  3. Note that your components won’t receive key as a prop. It’s only used as a hint by React itself. If your component needs an ID, you have to pass it as a separate prop: <Profile key={id} userId={id} />.

  4. <>...</> - this short hand does not accept the key={..} , so use a fragment instead.

So what to do ??
Instead, use a stable ID based on the data for the keys.

Why react components care about purity ??

React wants components to be pure becuase it cares about predictability . React wants that if we give a component same input 'n' times → same JSX should be produced , and rendering should not change anything outside the component.

But why react cares about predictability ??

- Because React may render your component more than once. For example, React may render, pause, restart, or re-render as part of its rendering process and development checks.

If your render function is pure: same input will give same output. but if on same input- there is a change in external variables then it will produce different outputs. And repeated rendering can produce weird results.

What is a side effect ?

Function ke main output/result ke alawa bahar ki duniya mein koi noticeable change karna ya interact krna = side effect. Ab woh synchronization hai ya nahi, woh task/purpose par depend karta hai. React docs ke according side effects rendering ke andar nahi hone chahiye. React docs specifically recommend event handlers for these changes.

okk..but why so - why react does not allow side effects while rendering ??
- Rendering is React's calculation phase like making a design of a home ( like desgining phase ). React needs this calculation to be safe to repeat or discard. Becuase react can render a component multiple times/restart render midway or abandon it completely.Therefore, don't make the outside world change while doing that calculation.

OK so why event handlers is a safe space to execute side effects ??
- Because event handlers do not run during rendering. Ony when the user intitates that event, the corresponsing event handler gets called. Likewise, while using useEffect, the side effect you perform (now syncing things in external system with react state/UI) is after the rendering has been completed by the react system. So even the callback jisme aap side effect run krte of use effect does not run during rendering.

What is external synchronization ??


- External means :  Something outside React.

For example:

Browser DOM
API/server
third-party library
WebSocket
browser APIs

- Synchronization means : Make two things agree with each other.

So External synchronization = React state/UI ko kisi outside system ke saath consistent rakhna.

Example - Say you want to update the browser document title with title count: dynamic value here, so you create a state : 

const [count, setCount] = useState(0); //react state currently : count = 0; //browrser: title count: 0 shows

Now, These two need to stay synchronized.If count changes to say 1 , then the browser title also needs to be updated but the browser's document.title is outside React's rendering system.

So you're synchronizing: React world & the Browser world . That's an external synchronization.


WHEN DO WE USE A USEEFFECT ??
So useEffect is useful when you need to say:
"After React has updated the UI, now I need to synchronize React with something outside of React system ." and not to run any peice of code after UI has been rerendered. 

eg:
useEffect(() => {
  document.title = `Count: ${count}`;
}, [count]);

Meaning:

count changes
      ↓
React renders
      ↓
UI updates
      ↓
effect runs
      ↓
browser tab title updated

Q : **What is rendering?**         
React running your component to figure out what UI should look like.                                            

Q : **Why pure functions?**                            
same inputs reliably produce same output, even if React renders again.                                       

Q : **Can I pass a global object and mutate it?**      
Yes technically, but that function is still impure. Passing it as an argument doesn't make mutation okay.       

Q : **Why `setCount` instead of `count = count + 1`?** 
`setCount` tells React that state changed and a new render is needed.                                           

Q : **What is external synchronization?**              
Keeping React's state/UI in sync with something outside React, like the DOM, video player, API connection, etc.
