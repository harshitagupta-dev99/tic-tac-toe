Why do we need to specify a key in react ?

KEY ANALOGY : 
File names in a folder and JSX keys in an array serve a similar purpose.

A key acts as a unique identifier of the item among its siblings. Even if the position of this item gets reordered due to sorting/insertion/deletion - the key lets React identify the item throughout its lifetime. 

2 rules of keys to be followed : 

  1. keys should always be unique - tbhi toh item ko properly identify krpayegi among its siblings 

  2. keys should not change - if keys changes everytime, then it wont match on rerenders and poora dom tree dobara recreate hoga and koi user input hui toh woh loose hojayegi + it will be very slow ( whole purpose of react will fail here !! )

Pitfalls : 

  1. Do not use array index as keys - coz jab elements reorder/insert/delete hote toh items upar neeche hote and indexing change hojati - violates our rule 2 that keys should not change - causes bugs 

  2. Do not generate keys on the fly e.g. with key={Math.random()} - again keys will change and never match up between renders, dom recreated everytime - slow krdega applicaiton ko + violates rule 2. 

  3. Note that your components won’t receive key as a prop. It’s only used as a hint by React itself. If your component needs an ID, you have to pass it as a separate prop: <Profile key={id} userId={id} />.

  4. <>...</> - this short hand does not accept the key={..} , so use a fragment instead.

So what to do ??
Instead, use a stable ID based on the data for the keys.

Why react components care about purity ??

React wants components to be pure becuase it cares about predictability . React wants that if we give a component same input 'n' times → same JSX should be produced , and rendering should not change anything outside the component.

But why react cares about predictability ??

- Because React may render your component more than once. For example, React may render, pause, restart, or re-render as part of its rendering process and development checks.

If your render function is pure: same input will give same output. but if on same input- there is a change in external variables then it will produce different outputs. And repeated rendering can produce weird results.

What is a side effect ?

Function ke main output/result ke alawa bahar ki duniya mein koi noticeable change karna ya interact krna = side effect. Ab woh synchronization hai ya nahi, woh task/purpose par depend karta hai. React docs ke according side effects rendering ke andar nahi hone chahiye. React docs specifically recommend event handlers for these changes.

okk..but why so - why react does not allow side effects while rendering ??
- Rendering is React's calculation phase like making a design of a home ( like desgining phase ). React needs this calculation to be safe to repeat or discard. Becuase react can render a component multiple times/restart render midway or abandon it completely.Therefore, don't make the outside world change while doing that calculation.

Ques : What is state isolation ?
- It basically means that when u render multiple instances of the same component, then every copy will get its own state. Changes/updates in state of one a particular copy will not affect the state of other copies.

Component instance = component ki ek rendered copy like below : 

<Counter /> #Counter1 --> own state : count = 5;
<Counter /> #Counter2 --> own state : count = 1;

Dono same Counter component/function se bane hain, but they are separate instances.

Ques : Is state private in react ?
- Yes, state is private meaning that it is private to the component in which it was declared. Meaning the parent component or other components do not have a control on it automatically & cannot access that state directly.

Example : 
function App(){
  <Counter /> 
}

function Counter(){
  const [count,setCount] = useState(0);
}

Here, the app is parent of counter. App renders counter so it knows that counter exists but it does not know automatically that counter mai jo count state hai uska value kya hai. for eg count = 7 hai . but app does not know that and it cannot control it as it does not have access to it directly. 

Ques : Then what is the diff bet state & props ?

- Props are used to pass data from parent to child components. Meaning parents have control over what it wants to send the child. The children cannot mutate the props as they are read only. 

- State is private to the component in which it is declared so the parent has no control over it directly. Parent cannot change the state defined in child component as it does not have access to it directly. This lets you add state to any component or remove it without impacting the rest of the components.

Ques : What if you wanted both counters to keep their states in sync? 
- The right way to do it in React is to remove state from child components and add it to their closest shared parent. 

State as a snapshot mental model : 

React stores state internally 
       ↓
Render happens
       ↓
React gives that render a snapshot : state --> count = 0 
       ↓
Component uses that snapshot
       ↓
Event handlers & asyc code ( like setTimeOut,etc) use that same snapshot
       ↓
setState(count+1)
       ↓
doesn't change current snapshot
       ↓
request another render . New render happens 
       ↓
React creates a NEW snapshot with the updated state --> count = 1
       ↓
Now Component uses this new snapshot
       ↓
Event handlers & asyc code ( like setTimeOut,etc) use this new snapshot

So in summary : 
Render 1 → state snapshot = 0
Render 2 → state snapshot = 1
Render 3 → state snapshot = 2

Important points to know : 
  1. State is maintained by react internally. It is not stored like normal variables in the function component. 

  2. setState() ke immediately baad changes nako dikhti..why ?? - coz setState() signals react to re-render the component with the updated val of state. Meaning that in next render the val will be updated. THe state variable val will remian same/fixed for the current render == snapshot bhi bolte. same for event handlers. 

  3. State variables val dont change inside the current render. Therefore, state update ka effect hamesha next render mai dikhega aapko.

  4. The old snapshot is never changed. Always a new snapshot is created on re-render.

  5. State is like a snapshot because a render receives a fixed version of state; calling setState doesn't change that current snapshot — it requests a new render, which receives a new snapshot.

  6. Every render has its own normal variables, functions, and event handlers. these dont survive the re-renders & Every render (and functions inside it) will always “see” the snapshot of the state that React gave to that render.

Updating objects in state 
-- iss topic mai mota mota React humko yeh bolra hai ki : agar state mein object hai toh usko directly change mat karo. Uski copy banao, and copy ko state mein set karo.

-- React state ko snapshot ki tarah treat karo — existing snapshot ko chhedo mat; jab change chahiye, naya snapshot do.

Be it primitive data types or reference data types , in react : 
State ko replace karo, existing state ko mutate mat karo.

mutate here meaning ==> do not change the contents of the state directly. 

Mental model : 

State
 ↓
Don't modify existing state

Create new value/object

kuch main 5-6 points hai jo sum up krte isko ache se : 
  
  1. Existing state ko mutate mat karo; state ko hamesha replace karo — primitive ho ya object/array.
  
  2. Primitives mein new value dete hain: setAge(age + 2).

  3. Objects/arrays mein new object/array banao, old data copy karo (...) aur changes karo.

  4. React primitives ko value se aur objects/arrays ko reference/identity se compare karta hai; new reference dene se React change detect kar pata hai.

  5. Jo variables React state ka part nahi hain, unhe normal JavaScript rules ke according mutate kar sakte ho. React ki “don’t mutate” rule specifically state ke liye hai.

Whenever we think about UI , there are 2 ways to go about it : 

1. Imperative:
   "UI ko kaise change karna hai step by step batao ?" Meaning --> “manually change UI” = directly tell individual DOM elements what to do.

2. Declarative (React):
   "Current state mein UI kaise honi chahiye ?" Meaning --> “UI kaisa dikhna chahiye for the given current state, bas woh batao. Kaise change karna hai woh React handle karega.”

React wants you to adopt #2.

So the imperative-vs-declarative discussion isn't saying:
“React has two different ways you normally use.”

It's teaching:
“React's whole philosophy is declarative, unlike the imperative DOM manipulation you might do with vanilla JS.”

Think of it this way:
React se pehle / React ke bahar, JavaScript mein tum UI ko directly manipulate kar sakti ho:

button.disabled = true;
message.textContent = "Submitting...";

That's imperative.

React aaya and said:
“Tum DOM ko directly manage mat karo. Tum bas state batao.”

setStatus("submitting");

And then:

<button disabled={status === "submitting"}>
  Submit
</button>

React handles the actual DOM changes.


Overall Crux : "In React, don't tell the UI how to change. Change the state, and describe what the UI should look like for that particular state."

Just these 5 points ka summary :

React is declarative → describe what UI should look like for each state; don't manually manipulate the UI.
Identify visual states → e.g. empty, typing, submitting, success, error. --> visual state meaning ki visually aapka UI kaise dikhna chahiye in a particualr state 
Identify what triggers transitions → user actions or computer events like network responses.
Store only essential state → don't store things that can be calculated from existing state.
Event handler → setState → render → UI changes.

Next topic is : how should one structure their state ??
- Meaning : “State mein kya-kya rakhna chahiye, aur state ko organize kaise karein so that it stays simple and doesn't create bugs?

5 rules :
1. If two pieces of state always change together, consider grouping them.

2. Avoid contradictory states - meaning -If two state variables should never be true at the same time, they probably should be one state variable with different possible values.

3. If you can calculate something from existing state or props during render, don't put it into state.

4. Avoid duplication in state - meaning : Store the ID/reference needed to identify something, rather than duplicating the entire object.coz sometimes u forget to update it and dono out of sync hojate
  - And why id ? Because : IDs help us identify which object we're currenlty talking about !!

5. Avoid deeply nested state - why ? --> The deeper the state, the more annoying updates become. So try to make the state flatter whenever possible so its easier to make the state updates for nested part.

🧠 Now let's connect all 5 rules . This is the part I'd actually remember.

When designing state, ask:

1. Are these things always changing together?
YES → Group them.

  eg: 
  position usually defined by (x,y) toh dono mostly sath hi update hore 

  const [position, setPosition] = useState({
    x: 0,
    y: 0
  });

  Instead of:

  const [x, setX] = useState(0);
  const [y, setY] = useState(0);

2. Can these states contradict each other? - means : Aisi state mat banao jisme impossible combinations ho sakti hain.
YES → Combine them into one state variable.

  eg:
  const [isLoading, setIsLoading] = useState(false);
  const [isLoaded, setIsLoaded] = useState(false);

  Could accidentally become:

  isLoading = true
  isLoaded = true // 🤨

  ✅ so we create a single state : 

  const [status, setStatus] = useState("loading");

  Possible values:

  "loading"
  "loaded"
  "error"


3. Can I calculate this from existing state/props?
YES → Don't put it in state.

eg: 
const [firstName, setFirstName] = useState("");
const [lastName, setLastName] = useState("");
const [fullName, setFullName] = useState(""); ❌

✅ imse fullname is redundant coz first name and last name se calc ho skta - why create extra state . usko sync mai rakhne ka alag jhanjhat
const fullName = firstName + " " + lastName;

4. Am I storing the same information twice?
YES → Remove the duplication. Maybe store the ID in state instead of the complete objects

  eg:

  const [products, setProducts] = useState([...]);
  const [selectedProduct, setSelectedProduct] = useState(product);

  Ab same product ki information 2 places par hai → out of sync ho sakti hai.

  ✅ so instead id store krlo , product retrieve toh baadmein hojayega usse.

  const [products, setProducts] = useState([...]);
  const [selectedId, setSelectedId] = useState(1);

  Then:

  const selectedProduct =
    products.find(product => product.id === selectedId);

5. Is my state deeply nested?
YES → Consider flattening it.
